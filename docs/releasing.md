# 版本发布

日常 `Checks` 工作流（`.github/workflows/ci.yml`）运行前端测试、浏览器测试、前端构建、Rust 编译检查和 Rust 测试，不生成安装包。

`Release draft` 工作流（`.github/workflows/release.yml`）在推送 `v*` 标签时启动。目前仅接受 `vX.Y.Z` 正式版本标签，构建 Windows x64 的 `.exe` 和 `.msi`。macOS 构建仍保持暂停，不代表通过了 macOS 验证。

## 准备版本

1. 在版本准备提交或 PR 中统一修改 `package.json`、`package-lock.json`、`src-tauri/tauri.conf.json` 和 `src-tauri/Cargo.toml` 的应用版本，并同步 Cargo 锁文件中的应用版本。
2. 在根目录 `CHANGELOG.md` 中编写对应版本的更新说明。文件不存在时先创建。版本章节使用二级标题，分类使用三级标题，例如：

   ```markdown
   # 更新日志

   ## [1.0.22] - 2026-10-28

   ### 修复
   - 写明用户能感受到的修复结果。
   ```

   也支持 `## 1.0.22` 或 `## v1.0.22`。发布说明取该版本标题之后、下一个二级标题之前的正文，保留其中的分类和 Markdown。不会使用整个 CHANGELOG，也不会自动生成说明。缺少文件、对应章节、正文或存在重复版本章节时，流程失败。
3. 合并到 `main` 后，给最终要发布的提交创建版本标签，再推送标签。标签必须指向已经进入 `main` 的提交，不要在尚未合并的 PR 分支上推送正式标签。

   ```powershell
   git switch main
   git pull --ff-only
   git tag -a v1.0.22 -m "TP v1.0.22"
   git push origin v1.0.22
   ```

以上版本和更新说明仅为格式示例，不表示当前仓库已有该版本的 CHANGELOG。推送前确认本地提交就是要发布的版本；不必等待 CI 结束再推送标签。

## 发布工作流

1. 检出标签，解析标签实际指向的提交（支持附注标签和轻量标签），核对提交已进入 `main`、版本文件一致，并提取该提交内的 CHANGELOG 条目。
2. 每 30 秒查询一次 `ci.yml`，只接受同一完整提交编号、`main` 分支、`push` 事件产生的 CI。已有成功结果时立即继续；运行中或尚未出现时最多等待 60 分钟。存在多次运行时选择最新一次；失败、取消或超时会停止发布，不重新执行 CI。
3. CI 通过后安装构建依赖，构建 Windows 安装包。Tauri 会执行生成安装包所需的前端构建和 Rust 编译，但不会再次执行测试或单独的 `cargo check`。
4. 创建标题为 `TP vX.Y.Z` 的 Release 草稿，以 CHANGELOG 对应版本的正文作为说明，并上传 `.exe` 和 `.msi`。同一标签的运行串行执行；重跑可以更新已有草稿并替换同名附件，拒绝修改已正式发布的 Release。
5. 在 GitHub 检查说明、下载并验证安装包，再手动发布草稿。这里没有配置安装包代码签名或自动正式发布。

如果等待失败，在 Actions 中检查该提交的 `Checks` 运行并解决问题，再重跑发布工作流。当前 CI 会取消同一分支上尚未完成的旧运行：若版本提交的 CI 被后续提交取消，需要重跑该提交的 CI；后续提交通过不能替代版本提交的结果。对于仅手动触发且没有 `main` 推送 CI 的提交，发布流程也不会放行。

工作流使用仓库自动提供的 `GITHUB_TOKEN`：等待结果需要 `actions: read`，创建草稿和上传附件需要 `contents: write`，无需配置个人访问令牌。若仓库或组织策略禁止这些权限，需要先调整对应策略。
